# 测试与证据

## SPEC 驱动

- 测试范围从 Requirement、Scenario、Target 和共享契约推导。
- 测试身份与数据先描述角色和特征，再根据当前环境绑定具体 Provider。
- 不扫描历史固定目录来猜测账号、数据、服务或测试入口。
- 后端 API 自动化是当前重点，但结构必须允许前端、契约、集成和端到端测试。

## 计划与执行分离

- `test-plan.md` 记录范围、环境需求、资源角色、自动化边界和通过标准。
- 自动化脚本属于相应 Target 仓库或独立可复用测试扩展，不嵌入需求模板。
- `verification.md` 只记录真实执行结果、验收和交付决定；计划、推断和模拟结果不能标记为通过。
- 大型日志、截图、抓包和报告放在 `evidence/`，由摘要链接引用并按 `.gitignore` 管理。

## 默认验证阶梯

验证按风险选择层级，后一层只补前一层不能覆盖的风险：

1. `Code Inspection`：检查本轮差异、目标仓库规范、公开契约、注释与文档、生成物一致性、静态分析和明显安全问题；存在阻断项时不得进入测试。
2. `Unit`：纯业务规则、边界条件和失败分支；不启动服务，不连接数据库。
3. `Focused Integration`：优先验证一个最小可回滚业务闭环，覆盖仓储、事务、软删除、迁移和数据库约束；只允许使用本轮获准的数据库。
4. `Runtime Smoke`：仅在 API、进程配置、序列化或动态契约等运行态风险存在时启动最少服务；默认先在 local 完成开发反馈，remote 只在测试方案明确要求兼容性、跨服务或最终交付确认时进入。
5. `Full Regression`：定向问题全部关闭后执行一次完整功能回归。
6. `Performance`：仅在需求、风险或用户明确要求时执行，并在测试方案中预先声明阈值。

Code Inspection 不是可选建议。涉及 API 或共享契约时，至少检查公开 DTO 字段说明、枚举值说明、XML/OpenAPI 文档生成配置，以及实际 OpenAPI 中对应参数和模型的 `description`。源码注释存在但未进入部署后的公开契约，仍视为未通过。

Deploy 不是日常实现反馈环的固定阶段，也不是每次测试重跑的前置动作。不得为了满足模板而部署、启动无关服务或联调 Scope 外系统；同一实现产物已经成功部署后，测试数据、用例或文档调整不得触发重新部署。

失败后先按测试运行器支持的 `case`、`tag` 或 `from-case` 定向重跑。不得每修复一个问题就重新执行完整回归；只有定向失败全部关闭后，才执行最终完整回归。

## 实现反馈环

- 开始修改前锁定本轮 Target、范围、非目标、执行模式、数据库授权和外部写操作；最新用户明确指令优先于个人默认模式。
- 从测试方案选择能暴露最高风险的最小垂直切片，先完成 `quick`，再完成 `focused`。持久化功能的 focused 场景至少覆盖“写入—状态变化—撤销或清理—零残留”。
- 自动化测试任务与对应实现任务相邻推进，不把全部业务测试推迟到代码和文档完成之后。
- 默认使用 `local` Profile 完成检查、增量构建、单元测试和可在本机闭环的 focused 验证；选择远端环境不代表每次代码修改后立即部署。
- 同一失败连续出现两次时停止盲目重建，先读取最内层异常、失败 SQL 或断言并确认根因。
- 修复期间只定向重跑失败场景；稳定后执行一次完整回归，并最后一次性生成验证资料。
- 只有服务实现或运行配置自上次成功部署后发生变化时才重新部署；数据库 reset 默认不得重建应用容器，迁移变化需要重启时必须显式执行。

## 数据库隔离与生命周期

- 会写数据库的集成、API 或回归测试必须使用 `manifest.json` 验证 Profile 声明的隔离环境。
- 推荐远端个人工作区使用 `dedicated-container`：容器、卷、端口和凭证均按开发者工作区隔离，端口只绑定远端回环地址。
- 隔离实例内部保留应用已有逻辑数据库名，避免因改库名产生跨库查询和迁移偏差。
- 项目必须提供 `provision`、`reset`、`status`、`destroy` 生命周期入口；销毁动作必须校验工作区、容器标识和项目标签。
- 凭证只保存在个人远端工作区的受限环境文件中，不进入仓库、命令输出或证据。
- Fixture 必须可重复执行，并在结束时验证零残留；不能清理的数据必须在结果中明确列出。
- `shared-instance` 仅用于项目明确接受的场景；不得把共享开发库当作默认自动化测试库。
- 用户明确授权 shared-instance 写入时，fixture 必须使用唯一业务标识、可逆操作和残留检查；不得把真实提交、配送或不可逆状态变化作为普通 Smoke。

## 执行环境门禁

- `apply` 和真实验证开始前必须执行 `pixcode debug gate apply|verify`，个人配置选择的执行模式是本轮运行态边界，不是提示信息。
- `manifest.json` 应为 `local` 和 `remote` 分别声明默认 Profile；新工作区和无个人配置场景必须落到安全的本地 Profile。
- Profile 只声明执行环境、隔离策略和通用生命周期命令。具体业务目录、服务拓扑、用例和迁移断言必须来自当前 change 的 test-plan 或 Target 测试资产，不得固化进全局 Profile。
- `remote` 模式下，本地构建、单元测试和临时启动只能作为辅助证据；远端部署、真实服务入口及其版本或指纹未确认前，不得声称完成远端调试或交付验证。
- 部署和重启是外部写操作。框架只负责门禁和证据约束，具体入口由项目声明，并且必须在用户授权范围内执行。
- 远端不可用、部署入口缺失或授权不足时明确失败或标记未执行，禁止静默回退到本地。
- 用户本轮明确指定执行模式时，Agent 应把该模式传给门禁；与个人默认 Profile 冲突时不加载该 Profile，不得继续折腾已被用户排除的环境。

## 输出与诊断预算

- 优先使用增量构建、`--no-build`、quiet/summary 模式和测试运行器筛选参数。
- 完整构建日志、既有警告和服务日志写入文件；对话只读取退出码、汇总、失败用例和最内层异常。
- 首次运行先验证最短命令和最少依赖，不为单个基础服务场景提前启动全部聚合与外部系统。
- 预计耗时超过测试方案预算或依赖初始化明显异常时，先汇报实际瓶颈，再继续高成本步骤。

## 安全

- 不提交账号、密码、Token、个人地址或生产数据。
- 不为测试擅自操作生产环境或未经授权的共享数据库。
- 环境或凭证缺失时记录为未执行并说明影响，不伪造证据。
