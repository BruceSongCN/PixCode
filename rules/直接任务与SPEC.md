# 直接任务与 SPEC

## 原则

SPEC 是显式交付模式，不是所有代码修改的默认流程。

## 直接任务

以下任务通常直接完成，不创建 OpenSpec change：

- 解释、评审、调查和故障定位；
- 恢复既有预期行为且不改变业务语义的缺陷修复；
- 局部重构、依赖、构建、日志、开发工具和展示配置调整；
- 不改变运行时共享契约、领域规则、权限、状态流程或持久化模型的实现变化。

直接任务仍应读取目标仓库规则，遵守《代码注释与提交》，并按风险执行最小充分验证。

## SPEC 任务

仅在以下场景进入 OpenSpec：

- 用户显式调用或要求 PixCode `propose`；
- 用户明确要求创建、维护、实现或归档某个 SPEC/change；
- 用户明确要求完整设计、跨端交付、正式测试交接或验收留痕。

若直接任务探索后发现必须改变业务规则或共享契约，应先说明触发原因并请求确认。不要自动创建 change，也不要通过兼容代码掩盖设计缺口。

## 资产归属

- `openspec/specs/` 是 OpenSpec 归档后的当前需求事实。
- `openspec/changes/<change>/` 只描述本轮 delta 和交付证据。
- `pix-specs/` 是归档后生成的当前完整功能结论，包含需求、设计、模型、流程、契约和测试策略。
- 模型、流程、契约和测试方案不复制可从代码稳定生成的全部细节。
- 不创建第二套编号、状态、门禁、追溯矩阵或归档机制。
