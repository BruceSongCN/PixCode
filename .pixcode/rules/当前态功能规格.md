# 当前态功能规格

## 定位

- `openspec/changes/` 保存活动变更，`openspec/changes/archive/` 保存不可变过程记录。
- `openspec/specs/` 保存 OpenSpec 原生当前需求事实。
- `pix-specs/` 保存 PixCode 面向评审、协作和交接的当前完整结论。
- `pix-specs/` 不是第二套 Change 生命周期，不维护独立状态机或需求编号。

## 目录与身份

- 功能资产支持任意层级中文目录和中文阅读型文件名。
- 每个功能叶子目录必须包含 `capability.yaml`，机器身份以其中稳定的英文 Capability ID 为准。
- 中文名称或分类层级可以通过新 Change 调整；目录名称不能替代 Capability ID。
- 同一个 Capability ID 在 `pix-specs/` 中只能出现一次。

## 归档映射

- 每个进入 PixCode 归档流程的 Change 必须包含 `pixcode.yaml`。
- `pixcode.yaml` 显式声明 Capability、中文发布路径、create/update 动作和本轮受影响资产。
- 一个 Change 可以影响多个 Capability；每个 Capability 分别合并和发布。
- 未列入 `assets` 的既有结论保持不变，不得机械重写。

## 当前态合并

- 需求基线以归档后 `openspec/specs/<capability-id>/spec.md` 为主要来源。
- 其他结论以“已有当前态资产 + 本轮归档设计 + 已确认实现事实”为输入。
- 输出必须描述当前完整状态，不保留 ADDED/MODIFIED、“本轮新增”或“计划实现”等过程表达。
- 标记“不适用”只说明本轮或当前没有相应设计，不能隐式删除既有结论。
- 删除或撤销既有结论必须通过新的 Change 明确表达。
- 发生冲突、缺少设计决定或无法判断替代关系时停止发布，不由 Agent 静默选择。

## 资产边界

- `010`—`080` 保存长期有效结论；每轮验证结果、验收例外和大型证据仍留在归档 Change。
- `090-变更追溯.md` 和各级 `README.md` 由 PixCode 根据 `capability.yaml` 重建。
- 不直接修改已经发布的业务语义。需要修正时创建新 Change，再执行归档发布。
- `capabilities finalize` 只在全部受影响资产已经完成语义合并、无占位符且标明来源 Change 后执行。
